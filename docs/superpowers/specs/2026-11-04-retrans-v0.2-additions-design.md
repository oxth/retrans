## Part A — Settings survive quit, update and reinstall

**Intent.** Whatever the user configured stays exactly as they left it after quitting, auto-updating, or downloading and installing a new version over the old one.

**Rules.**
- **Where state lives:** all user state stays in the app's data folder (`~/Library/Application Support/com.retrans.app/` on macOS, `%APPDATA%\com.retrans.app\` on Windows). That covers prefs, recent projects, MT settings, downloaded models, update preferences, window state and open tabs. Installers and the updater never touch this folder.
- **App identity:** the identifier `com.retrans.app` must never change again.
- **Versioned prefs:** the prefs file carries a `prefsVersion`. On load, older versions are **migrated** and never reset; unknown future fields are kept, not dropped.
- **New remembered state:**
  - window size, position and maximized state;
  - open workspace tabs and the active tab (Part B);
  - per-project view mode (already exists).
- **Secrets:** API keys (Part D) go in the OS credential store (macOS Keychain, Windows Credential Manager), never in prefs or project files. They survive updates and reinstalls too.
- **Real installs:** v0.1.0/v0.1.1 users already have prefs with no `prefsVersion`. The migration must read those real files, not just a test fixture: treat a missing `prefsVersion` as version 1.
- **Keychain prompt (owner decision):** API keys use the OS credential store. The macOS app is only ad-hoc signed, so after an update macOS may ask once to allow Retrans to read its Keychain item. That is accepted. The key is never lost, and Retrans must handle a denied or cancelled prompt gracefully: show "Couldn't read the API key — re-enter it in Settings" and don't crash.
- **Quality bar:** a test loads prefs written in the shape of every earlier version (the v0.1.0 shape is the baseline) and checks nothing is lost. A Rust/integration check confirms the data folder path doesn't depend on the app version.

## Part B — Workspace tabs

**Intent.** Work on several projects or workspaces at once and switch between them instantly.

**Behaviour.**
- **Tab bar:** a tab bar sits above the main screen, one tab per open project or workspace, labelled with the project name and an unsaved dot.
  - **Open project** and **Create new project** open a new tab, or switch to it if it's already open.
  - Tabs can be closed with an × button.
- **Independent tabs:** each tab keeps its own session:
  - data and unsaved edits;
  - crash-recovery journal;
  - file watching and TypeScript/Figma source sync;
  - conflicts;
  - filters and view mode.
- **Work in background tabs:** a "Translate missing" run, a download or a sync in a background tab continues. The tab shows a small activity marker.
- **Closing:**
  - Closing a tab with unsaved changes asks Save / Don't save / Cancel (as closing a project does today).
  - Quitting the app asks once, listing the tabs with unsaved changes.
- **Restore:** open tabs and the active tab are remembered (Part A) and restored on next launch. A tab whose folder is gone is skipped with a notice.
- **Watchers:** today the app runs one file watcher at a time. With tabs, one watcher runs per open tab.
- **Limits:** none set. Memory per tab is the project's size. *(My call.)*
- **Auto-save (owner decision, during the build):** edits are written to the project files about a second after the last change, in every tab, background tabs included. Save (Cmd+S) still saves at once.
  - A tab with unresolved conflicts waits until they are resolved.
  - There is no "Restore unsaved changes?" prompt. Edits left by a crash are put back automatically on the next open, then auto-saved.
  - The quit and close prompts remain only for that rare case: a tab that still has unsaved changes because it couldn't save.
- **Startup (owner request, during the build):** Settings → Startup → "When Retrans opens": **Reopen the projects that were open** (default) or **Show the start screen**.

## Part C — Figma Variables

**Intent.** Designers keep UI text in Figma Variables, with one mode per language. Those strings must be translated in Retrans, go into the **app's code**, and also go **back into Figma** via re-import, without changing the Figma variable names.

### C1. The format (from the owner's example `ENG.tokens.json`, `TH.tokens.json`)
- **One file per mode:** Figma exports one W3C Design Tokens (DTCG) file per mode. The mode name is in the root `$extensions["com.figma.modeName"]` (e.g. `ENG`, `TH`).
- **Each variable** is an object with:
  - `$type` (`string` for text);
  - `$value` (the text);
  - `$extensions` with `com.figma.variableId`, `com.figma.scopes` and `com.figma.type`.
- **Groups:** nested objects are groups (Figma `Group/Sub/Variable`). Key paths join them with `.` *(my call)*.
- **Variable names:** can be any text, including Thai sentences (`"สวัสดี คุณ"`).
- **Non-text variables:** variables with `$type` other than `string` (colors, numbers, booleans) are ignored for translation and **passed through unchanged** on export back to Figma.
- **Builder check:** confirm this against Figma's current Variables import/export docs before implementing.

### C2. Bringing Figma into a workspace
- **Workspaces only** *(my call)*: Figma sources are supported in workspaces (imported TS projects and format-free projects). Direct-edit JSON/Paraglide projects stay as they are.
- **Opening a Figma folder directly (owner request, 2026-11-05):** Open project on a folder that holds only Figma Variables files offers **Create a workspace from Figma files**. The user confirms each mode's language and the base language. The folder becomes a workspace whose Figma folder is the folder itself (`dir: "."`); the files stay where they are and aren't changed. Strings land in the group `figma`.
- **Source:** Figma is a **second kind of source** for a workspace, next to TypeScript. A workspace can have both, e.g. `axons-cms` with its TS locales **and** Figma files.
- **Folder:** Figma files live in a project folder, `design/figma/` by default (configurable). **Import Figma files…** copies the picked `.tokens.json` files there. Retrans watches the folder and syncs automatically, like TS sources.
- **Modes and languages:** each mode maps to a language code.
  - Retrans suggests a code (`TH` → `th`, `ENG`/`EN` → `en`, using known names and codes, else asks).
  - The user confirms once, and the mapping is stored in the workspace.
- **Group:** Figma variables appear as their own group, named after the collection/file *(my call)*.
- **Identity:** variables are identified by their **Figma variable ID**. A variable renamed in Figma keeps its code key, link and translations.
- **Sync:** same three-way rules as TS sync (workspaces spec §7):
  - new variables are added;
  - a changed value with no local change is taken;
  - deleted variables are flagged "removed in source" for the user to confirm.

### C3. Figma name vs code key
- **Figma name:** the variable's name in Figma. It is never changed by Retrans and is used for export back to Figma (together with the variable ID).
- **Code key:** optional, assigned later in Retrans (e.g. `welcome_message`), and used when the string goes into the app's code. It must be unique across the workspace and valid for the target format.
- **Unmapped strings:** until a code key is assigned:
  - **write-back to the original TS files skips them** *(my call)*, so Thai-sentence keys never land in the codebase;
  - exports to another folder or format (JSON, Paraglide, TS modules) use the Figma name as the key;
  - those rows show "No code key yet";
  - the Export dialog says how many are unmapped.

### C4. New strings vs strings that already exist in code
- **New string:** assign a code key and pick the target TS file/group. The next write-back adds it there like any new key.
- **Existing string:** **link** the Figma variable to an existing code key (e.g. `button_save`).
  - Retrans **suggests** likely matches by comparing base-language (and other) text. The user confirms.
  - Linked strings are **one translation**: editing in Retrans updates the code on write-back and the Figma variable's `$value` on Figma export.
- **Conflicts (owner decision):** when Figma and code both changed a linked string since the last sync, Retrans shows a **git-style conflict** in the existing conflict window:
  - "From Figma" and "From code", with the original underneath;
  - the user picks one or edits a final version;
  - exports are blocked while a conflict is open.

### C5. Export back to Figma
- **Scope** *(my call)*: the Figma export only contains variables that came from Figma (including linked ones). Strings that exist only in code or were created in Retrans are never written as new Figma variables, so re-import can't create duplicates.
- **New export kind:** **Figma Variables (.tokens.json)**, one file per mode, written to a chosen folder (or back into `design/figma/`).
- **What changes:** only `$value` of string variables changes. Everything else is preserved, so Figma re-import updates existing variables instead of duplicating them:
  - names, nesting, `$type`;
  - `$extensions` (variable IDs, scopes);
  - non-string variables;
  - key order, indentation and the file's mode `$extensions`.
- **Untranslated strings:** a mode with no translation for a string keeps that variable's existing `$value` (Figma needs a value per mode). If the variable is new to that mode, it gets the base-language text and a warning lists them *(my call)*.
- **New languages:** a language added in Retrans becomes a new mode file, containing every exported variable. The user creates the mode in Figma when importing.
- **Placeholders:** the existing placeholder checks apply. The example already has a real mismatch: English `{{neme}}` vs Thai `{{name}}`.

## Part D — AI translation providers, multi-language runs, custom instructions

**Intent.** Use the AI the owner already pays for (Claude, ChatGPT), or any OpenAI-compatible API, instead of, or besides, the built-in local model. Translate several languages in one go, and steer tone and terms with instructions.

### D1. Providers (Settings → Machine translation)
1. **Built-in local model:** unchanged, offline, and the **default**.
2. **OpenAI (ChatGPT):** API key plus a model picker.
3. **Claude (Anthropic):** API key plus a model picker.
4. **OpenAI-compatible:** base URL, API key (optional for local servers) and model name. Covers OpenRouter, Groq, DeepSeek, Together, Ollama, LM Studio and others.
5. **ACP agent:** Retrans acts as an **Agent Client Protocol client**. It starts a locally installed agent that speaks ACP over stdio and sends it translation work.
   - Agents: Claude Code via its ACP adapter, Codex, Gemini CLI, or any ACP agent with a configured command.
   - The agent uses the user's existing subscription login. No API key.
   - **Safety:** Retrans advertises **no** file-system or terminal capabilities and **automatically refuses every permission request**, so the agent can only reply with text.
     - **Correction (review, 2026-11-05):** this stops the agent from using *Retrans's* file and terminal access, and from getting any permission it asks for. It doesn't stop an agent's own built-in tools, such as Claude Code's read-only file tools, which don't ask. Retrans therefore:
       - runs the agent in an empty temporary folder and opens a fresh session per request;
       - tells the model the strings are text to translate, never instructions;
       - says plainly in Settings that an agent's own tools can still read files on this computer;
       - recommends an API provider for text from people the user doesn't know.
   - **Builder check:** verify method names and adapter commands against the current ACP spec and the agents' docs.

- **Scope:** the provider is chosen globally, with an optional per-project override.
- **Keys:** stored in the OS credential store (Part A).
- **Test:** "Test this model" works for every provider and shows the exact instructions sent.

### D2. Privacy (amends the original anti-goal "translation text leaving the machine without the user knowing")
- **Opt-in:** cloud providers and ACP agents are **opt-in**. Turning one on shows a one-time confirmation naming where text goes.
- **Visible:** while a cloud or agent provider is active, the translate UI shows its name ("Translating with Claude…").
- **Local stays default.** Network use is now: model downloads, update checks, and the cloud/agent provider the user turned on.

### D3. What is sent (cloud and ACP)
- **Per string:**
  - the masked text (placeholders protected exactly as today);
  - key name;
  - group/file;
  - base-language text;
  - existing translations in other languages;
  - the combined custom instructions (D5).
- **Batching:** strings are batched (several strings and several target languages per request, with a structured JSON reply) to reduce cost.
- **Same safety checks on every result:**
  - placeholder tokens are restored and verified, otherwise "Couldn't translate safely";
  - results are marked machine-translated / needs review, never Reviewed.
- **Errors** are shown with the provider's message: bad key, rate limit, network. Rate limits back off and retry a few times.

### D4. Translate missing — several languages at once
- **Choosing:** "Translate missing…" lets the user **tick several languages** (plus "All languages"), keeping the namespace/group filter.
- **Progress:** shown per language and overall. Cancel stops everything, and finished results stay.
- **Batching:** with cloud/ACP providers, a string's target languages go in one request.
- **Providers:** works with every provider.
- **Editor suggestions:** the cell-editor suggestion stays for the language being edited.

### D5. Custom instructions
- **Levels, combined in this order:**
  1. **All projects** (Settings): e.g. "Keep translations short, this is UI text."
  2. **This project** (stored in the workspace/project `.retrans/`, shared through git): e.g. "Formal Thai. Keep [Product Name] in English."
  3. **This language in this project:** e.g. for `ja`: "Use です/ます form."
- **Where they apply:**
  - sent to all cloud and ACP providers;
  - on for the Qwen local models;
  - off for TranslateGemma, whose prompt format is fixed. Settings says so.

## Anti-goals (additions)
- Losing user settings on update or reinstall.
- Changing a Figma variable's name, ID or non-text value.
- Duplicating Figma variables on re-import.
- Any cloud call without the user having turned that provider on.
- An ACP agent reading or writing files or running commands.
- API keys in project files, prefs or logs.
- Machine output marked Reviewed.
- Silently resolving a Figma vs code disagreement.

## Quality bar
- **Settings migration test** (Part A).
- **Tabs:** independent sessions, background run continues, close/quit prompts, restore on launch.
- **Figma:**
  - round trip on the owner's example files: import, then export back with no edits, gives byte-identical files;
  - one edit changes only that `$value`;
  - renamed-in-Figma variable keeps its links;
  - linking and conflict flows;
  - code export with and without code keys.
- **Providers:**
  - each tested against a local fake server (OpenAI-style, Anthropic-style, ACP fake agent over stdio);
  - placeholder safety and batching;
  - permission requests refused;
  - no network call when only the local model is enabled.

## Left to the builder

- ACP library vs a small hand-written client.

## Calls I made (owner to check)
- Figma key paths join groups with `.`. Figma gets its own group per collection/file. Figma files are copied into `design/figma/`.
- A new-to-mode untranslated Figma variable is exported with the base text plus a warning.
- Per-project provider override.
- Custom instructions on for Qwen and off for TranslateGemma.
- No tab limit; a missing folder's tab is skipped on restore.
- Build order: A → B → C → D.
- Figma works in workspaces only.
- Unmapped Figma strings are skipped by TS write-back.
- The Figma export contains only Figma-origin variables.
